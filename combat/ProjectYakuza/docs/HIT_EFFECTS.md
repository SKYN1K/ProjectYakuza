# Consistent animated world aura, 0.14.6

All aura effects now use the same OnPostRender world-camera path, for every facing. The temporary attachment created by WorldEffects.attach is transferred out of the character's automatic attachment list using ArrayList.remove(instance), without disposal. HeatAura exclusively owns that native instance until cleanup. This removes the direction-dependent automatic draw rather than drawing a second copy over it. The callback uses N consistently, matching the former up-right path. It calls sprite.update(instance) once before each native instance.render call. Native GameTime handles frame delta and pause; native sprite looping wraps the 32-frame animation. The current camera's local player is the only owner rendered in its pass. No UI element or screen projection is involved.

Animation also has visibly travelling upward brightness bands over the original smooth rim alpha, alongside the subtle looped shear/pulse. The pixelated atlas remains absent. Source dimensions, size and four upper-body positions are unchanged from v0.14.5. Stable heat owns exactly four instances per player, at most sixteen for four local players. There is no additional OnTick or player-update event. The render hook exists only while effects are active; cleanup disposes/pools owned instances exactly once without touching other character attachments. Save/menu/death/unequip/toggle/fuel cleanup is preserved. Burning characters use the same explicit path, without a second automatic fire attachment draw for this aura.

Validation: 794 Kahlua checks cover combat and manual ownership, all-eight-facing draw consistency, explicit update/loop, pause handling, independent attachments, pooled cleanup and heat transitions. AuraAnimationProbe runs actual B42 classes: attachment ownership transfers without disposal, explicit update advances frame 0 to 3.5556 after eight updates, loops within 32 frames, and returns the instance to the native pool. WorldAnchorProbe and alpha bounds retain upper-body placement. Source inspection verifies OnPostRender is inside the world camera frame, before UI. Live GPU filtering, motion and all-facing appearance still require a game check. Flat sprite effects do not gain per-limb volumetric occlusion from this change.

Earlier implementation notes follow for provenance and history; the automatic-attachment/facing-fallback descriptions below are superseded by the ownership/rendering above.

# Aura sizing update, 0.14.5

The smooth flame-rim component is approximately 15% wider and 30% taller than v0.14.4 (51x83 source drawing at half sprite scale versus 22x32 previously). Four patch centres expand about the existing lower cutoff at height 24. Frames increase from 32x48 to 64x96, retaining higher source detail. The older e_j_0076 low-resolution animated atlas component is entirely removed from the frame builder and asset manifest. Only e_j_0073_aura_dA8L8.dds and e_j_0073_aura_cA8L8.dds remain. A gentle cyclic shear and pulse animate these smooth rims. The existing missing-facing world callback is unchanged. Coverage checks confirm no visible pixel reaches the leg area. Native projection and 646 Kahlua checks pass; exact in-game size still needs a visual check. Stance/attack rollback hashes are unchanged.

# Native world hit sparks and heat aura, 0.14.4

Sparks use 16-frame normal/strong animations: a short original-texture impact flash followed by individually travelling golden streaks and fade, lasting 240/280ms at normal time. The original Yakuza 6 fan/glint textures are retained, with provenance in hit-effect-assets.json. Revised frame hashes are in world-hit-spark-assets.json. This approximates the flash/scatter motion in Yakuza; it does not reproduce the original Dragon Engine emitter or shader exactly.

Native B42 character rendering passes (offsetX + tileScale, offsetY - 89*tileScale) to every attachment. IsoSprite then additionally subtracts half the scaled texture width and its full scaled height for moving objects. WorldEffects.attach accounts for both operations. Native projection reproduced the old centre at (-66,-2) pixels relative to feet and the corrected centre at (0,-52) for a normal tileScale=2 torso impact. Ground impacts use 6*tileScale height. Each small aura frame uses scale tileScale/2 and its emitter's own horizontal/height offset. Alpha padding avoids solid overlays. Camera/zoom/jitter are handled by native world rendering.

Sparks still require confirmed positive-damage local style hits and deduplicate victims per native strike. At most six per player and 24 total are active. Cached sprite slots are bounded, and the cleanup OnTick callback exists only while sparks are live. It removes owned instances by identity plus parent sprite and preserves unrelated attachments. Save/menu/death/expiry/toggle cleanup remains. Both variants end in a transparent frame.

The 0.14.2 heat aura uses four compact overlapping upper-body patches: torso at (0,32), arms at (-5,32)/(5,32), head at (0,44), in tile-scale units relative to feet. Their scales are tileScale times 0.5/0.4/0.4/0.325. This replaces the wide six-emitter shoulder/arm/waist arrangement; there are no leg, waist, orbit or outward-drift emitters. The native attachment stays with the character root, rather than being individually attached to an animated limb bone. A coverage check evaluates every frame's actual alpha bounds: visible pixels remain at least 24 units above the feet and within 10 units horizontally of the body centre. This is a configured upper-body region, not a per-pixel skin-occlusion test.

The source files are original Yakuza 6 particle.par raw_event/e_j_0073_aura_dA8L8.dds and e_j_0073_aura_cA8L8.dds (thin flame rims), plus e_j_0076_aura_gA8L8.dds (8x8 animated wisp sheet). Three phase-offset 32-frame loops combine the original rim alpha and animated cells with cyan/blue tint, a subtle pulse and fixed centres. No artificial orbit, broad full-body image or newly generated flame texture is used. Source/output hashes are in heat-aura-assets.json. This is a new Zomboid composition using Yakuza assets, not the exact Dragon Engine shader or emitter. Flat native sprites still approximate depth and cannot wrap/occlude behind each body part like volumetric effects.

HeatAura maintains four native attachments per eligible local player, at most 16 for four local players. One completed stock enables them; Extreme Heat retains them while fuel remains. They hide below threshold, on death, vehicle entry, unequip or their saved visual toggle. Eligibility is refreshed by heat/style/Extreme events and the existing throttled 100ms Heat.update. Stable state reuses all sprites/instances; an externally removed emitter alone is recreated. Save/menu cleanup removes only owned instances. No extra aura OnTick, UI object, dynamic light, model refresh or map object is created. WorldEffects.attach converts each patch's horizontal/height offset; native projection verifies all four positions.

Directional fix: B42.21 IsoSprite.renderCurrentAnim_FBORender has a special NW branch that draws only wall-shaper consumers and skips an ordinary character attachment. A.render uses OnPostRender, which IngameState invokes inside each world camera frame after IsoWorld.render and before EndFrame/UI drawing. Only for the current camera's local aura owner facing NW, it renders the four existing instances through their native render API with N. Native character updates still advance those same instances. Other facings receive no additional draw; burning characters are excluded because their native attachment path already forces N. The fallback hook is removed when no aura instances exist. No UI element or screen overlay is introduced. This workaround targets B42's default FBO renderer; alternate debug/legacy render paths are untested.

Native character code repositions all attached sprites when on fire; burning-character appearance still needs live validation. Native scene visibility applies to the attached effect, but this is a flat animated sprite, not a 3D volumetric aura. It follows the character rather than individual limb bones. Multiplayer replication and exact Yakuza timing are not implemented.
